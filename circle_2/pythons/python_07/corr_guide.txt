#### ✅ Check: "Does get_deck_stats() provide meaningful information?"

**Location:** `ex1/Deck.py`
```python
def get_deck_stats(self) -> dict:
    if len(self.cards) == 0:
        return {
            'total_cards': 0,
            'creatures': 0,
            'spells': 0,
            'artifacts': 0,
            'avg_cost': 0.0
        }
    
    # ✅ Counts different card types
    creatures = sum(1 for card in self.cards if card.__class__.__name__ == 'CreatureCard')
    spells = sum(1 for card in self.cards if card.__class__.__name__ == 'SpellCard')
    artifacts = sum(1 for card in self.cards if card.__class__.__name__ == 'ArtifactCard')
    
    # ✅ Calculates average cost
    total_cost = sum(card.cost for card in self.cards)
    avg_cost = total_cost / len(self.cards)
    
    # ✅ Returns useful statistics
    return {
        'total_cards': len(self.cards),
        'creatures': creatures,
        'spells': spells,
        'artifacts': artifacts,
        'avg_cost': round(avg_cost, 1)
    }
```

**Answer:** ✅ YES (provides counts and average cost)

### Question 1: "Can the learner explain why abstract classes are useful?"

**WHAT YOU SAY:**

> "Abstract classes are useful because they create a **contract** that all subclasses must follow.
>
> For example, in my project, the `Card` abstract class ensures that ALL card types (Creature, Spell, Artifact) have the same methods like `play()`, `get_card_info()`, and `is_playable()`.
>
> This is useful because:
>
> 1. **Consistency** - The game engine can rely on every card having a `play()` method
> 2. **Prevention of errors** - Python won't let me create an incomplete card that's missing required methods
> 3. **Clear documentation** - When I look at the Card class, I immediately see what every card must implement
>
> Without abstract classes, someone could create a card without a `play()` method and the game would crash. Abstract classes prevent this at the design level."

### Question 2: "Can the learner explain the benefits of interfaces and multiple inheritance?"

**WHAT YOU SAY:**

> "Interfaces and multiple inheritance allow you to **compose objects from multiple capabilities** instead of inheriting everything from one big class.
>
> For example, in Exercise 2, I have:
> - `Combatable` interface - for cards that can fight
> - `Magical` interface - for cards that can cast spells
>
> The benefit is **flexibility**:
> - A pure fighter card can be `Card + Combatable` (no magic methods cluttering it)
> - A pure mage card can be `Card + Magical` (no combat methods it doesn't need)
> - An elite card can be `Card + Combatable + Magical` (has both abilities)
>
> This follows the **Interface Segregation Principle** - classes shouldn't be forced to implement methods they don't use.
>
> Multiple inheritance lets me mix and match these interfaces like LEGO blocks to create exactly the card I need."

### DESIGN CHOICE DISCUSSIONS

Be prepared to discuss these design decisions:

#### **Design Choice 1: Why use abstract base classes?**

> "I chose to use abstract base classes to create a **contract** that all cards must follow.
>
> **Alternative I rejected:** Just using regular inheritance without ABC
> - Problem: Nothing prevents someone from creating an incomplete card
> - Someone could inherit from Card but forget to implement `play()`
> - Game would crash at runtime
>
> **Why ABC is better:**
> - Python prevents instantiation of abstract classes
> - Forces all subclasses to implement required methods
> - Errors caught at creation time, not at runtime
>
> This is a **defensive programming** choice - prevent bugs early."

---

#### **Design Choice 2: Why separate Combatable and Magical interfaces?**

> "I separated combat and magic into different interfaces following the **Interface Segregation Principle**.
>
> **Alternative I rejected:** One big interface with all methods
>
> **Problems with that:**
> - A pure spell card doesn't attack, but would have to implement `attack()` and `defend()`
> - Would have to write dummy implementations or raise NotImplementedError
> - Violates the principle: 'Classes shouldn't be forced to implement methods they don't use'
>
> **My solution:**
> - `Combatable` interface for combat methods
> - `Magical` interface for magic methods
> - Mix and match as needed
>
> **Benefits:**
> - SpellCard only implements Card + Magical (no unused combat methods)
> - CreatureCard only implements Card + Combatable (no unused magic methods)
> - EliteCard implements Card + Combatable + Magical (needs both)
>
> This is **modular design** - compose objects from focused interfaces."

---

#### **Design Choice 3: Why use Strategy and Factory patterns?**

> "I used the Strategy and Factory patterns to achieve **runtime flexibility**.
>
> **Alternative I rejected:** Hardcoded behavior
>
> **Problems:**
> - To add SciFi theme: Edit GameEngine code
> - To add defensive strategy: Edit GameEngine code
> - Violates **Open/Closed Principle** (open for extension, closed for modification)
>
> **My solution:**
> - Strategy Pattern: Encapsulate AI behavior in swappable classes
> - Factory Pattern: Encapsulate card creation in swappable classes
>
> **Benefits:**
> - Change theme without touching GameEngine
> - Change AI without touching GameEngine
> - Mix and match - 9 combinations from 3 factories × 3 strategies
>
> This is **extensible design** - add new behaviors without modifying existing code."

---

#### **Design Choice 4: Why use absolute imports?**

> "I used absolute imports (`from ex0.Card import Card`) instead of relative imports.
>
> **Alternative I rejected:** Relative imports (`from ..ex0.Card import Card`)
>
> **Problems with relative imports:**
> - Only work when running as a package
> - Break if you move files
> - Harder to understand the import path
>
> **Benefits of absolute imports:**
> - Clear where imports come from
> - Work consistently
> - Standard in professional Python projects
> - Required for my project structure (exercises importing from each other)
>
> This is **explicit design** - code should be self-documenting."
